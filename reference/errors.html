Error format​

Most errors from data endpoints are a JSON object with a message:

{ "message": "Please validate order data. Shipping Address 1 can not be empty for Pick Ticket Id PT-0001001" }

Two exceptions: the token endpoint uses the OAuth error shape, and a failed order save on Submit orders returns {"accepted": false} (see Retrying order submissions).

The token endpoint's error shape
{ "error": "invalid_credentials", "error_description": "A valid client_Id and client_Secret must be provided." }
Match on the status code

Read the HTTP status first, then the message. Messages are written for people; match on the status code in your code, not on message text.

Status codes​

StatusMeaningRetry?What to do

400The request is invalid: malformed JSON, a missing or invalid field, or your account could not be validated.NoFix the request. Validation messages name the field and the pick ticket.
401Missing, malformed or expired token.Once, with a new tokenGet a new token and retry once. If it fails again, check your credentials.
404None of the orders you asked for has been picked, and none is currently picked (Get picked orders).NoCheck the IDs; use shipment confirmations for shipped orders.
410You called a path kept only for older integrations.NoUse the current /api/v1/ path named in the message.
415The Content-Type is not JSON. Returned only by Submit orders, Submit receiving orders, Get receipt confirmations, Get inventory and Get inventory by lot and LPN.NoSend Content-Type: application/json (text/json is also accepted).

The Partner API does not currently return 403, 409 or 429. Handle any other 4xx as "do not retry" and any other 5xx as "retry with backoff", so your integration keeps working if new codes are introduced.

No data is not an error​

When nothing matches, some read endpoints answer 200 with a message instead of an empty list:

{ "message": "No records found. Please check input." }

Check the shape of a 200 body before you read it as data.

Retrying order submissions​

Order submission is the one call where a retry could create duplicates, so it is handled specially.

After a 400:

A 400 can mean some orders were accepted

When individual orders fail validation, every valid order in the request is still accepted, and the 400 names one failed order and its reason, not every failure. Resend only the orders that failed: check each against the field rules to find them all.

Nothing was accepted when the 400 is Invalid Input, Unable to validate client., or Please validate order data. with no detail.

After a 500 or 504 with {"accepted": false}: some orders may have been accepted. Resending the same request within 24 hours is generally safe: orders already accepted with identical content are recognised and skipped.

After a timeout with no response at all:

Do not resend orders automatically after a timeout

If a Submit orders request times out with no response, the orders may have been accepted in full, and the API returns no order IDs you could check. Resending can create duplicate orders. Contact Capacity Support with the time of the request, the pick tickets and the X-Correlation-ID you sent.

Backoff​

Wait 2 seconds before the first retry, then double the wait each time (2, 4, 8, 16 seconds), adding up to a second of random jitter. Stop after five attempts and alert someone.

Correlation IDs​

Send an X-Correlation-ID header with a unique value (a UUID) on every request. It is returned on the response. Log it with the request, and when you contact support quote it together with the time of the request and, for orders, the pick tickets.

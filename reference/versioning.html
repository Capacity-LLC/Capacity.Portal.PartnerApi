Versioning and changes

The version is in the path: every current operation is under /api/v1/.

Changes that can happen within v1​

These changes are not breaking. They can be made to v1 at any time and are listed in the changelog. Build your integration so that they do not break it:

  • New operations.
  • New optional request fields.
  • New response fields. Ignore fields you do not recognise.
  • New status codes. Handle an unknown 4xx as "do not retry" and an unknown 5xx as "retry with backoff".
  • Changed message text. Match on the status code, never on the message.

Breaking changes​

These are breaking: removing or renaming a field or operation, making an optional field required, changing a field's type or format, or tightening a limit such as a maximum length.

Capacity checks every change to the API's contract for breaking changes before it is released. A breaking change to v1 is listed in the changelog.

Previous REST API paths​

The paths of the previous Capacity REST API are kept for existing integrations and marked deprecated in the OpenAPI document. New integrations must use the /api/v1/ paths; see Previous REST API paths.

The OpenAPI document​

The complete v1 contract is published at /openapi/partner-api.v1.json. It changes whenever the API reference on this site changes, so you can generate a client from it or compare versions.
